# 実績値・営業データ 整合性検証レポート

- 作成日: 2026-05-30
- 対象: `marketing/digilab_beauty_flyer.html` の実績値、`db/digilab_beauty.db`、`db/esthetic_industry_dd_19companies.csv`
- 目的: 営業資料に使う前に、主張の根拠が社内データに存在するかを検証する

---

## 1. 結論（要約）

チラシ記載の実績値（**顧客満足度98% / リピート率向上150% / 業務効率化40% / 最短2週間**）を
裏付けるデータは **社内に存在しない**。現状はB2B営業の**リード段階で受注ゼロ**であり、
これらの数値を「自社実績」として外部提示すると**景品表示法（優良誤認表示）リスク**がある。

加えて、営業リストとDBに **データ品質の問題が3件** 見つかった（§3）。

---

## 2. 実績値の根拠検証（DB 実データ）

| チラシの主張 | 根拠データ | 判定 |
|---|---|---|
| 顧客満足度 98% | `kpi_tracking` テーブル = **0行（空）** | ❌ 根拠なし |
| リピート率向上 150% | 同上。実績値を記録する場所が空 | ❌ 根拠なし |
| 業務効率化 40% | 同上 | ❌ 根拠なし |
| 最短2週間で導入 | 導入実績テーブル該当なし／`documents`=0行 | ❌ 根拠なし |

補足: パイプライン実態
- `sales_pipeline` = 54行すべて **stage「リード」・確度10%・受注額(expected_value) None**
  → **受注・導入実績はゼロ。全社が初期リード段階。**
- `contacts` = 0行 / `contact_history` = 0行 / `documents` = 0行
  → 実際の接触履歴・商談記録・納品物が**まだ登録されていない**。

→ つまり実績値は「目標値・期待値」を実績のように表示している可能性が高い。
   営業利用の前に「実績」か「目標」かを明示的に区別すること。

---

## 3. 営業データの品質問題（要修正）

### 問題① companies テーブルの3重登録
- `companies` = **54行**だが、ユニーク企業名は **18社**（各社がちょうど3回ずつ重複登録）。
- 原因: DBインポート処理（`scripts/main.py` 周辺）を複数回流したと推測。
- 影響: 集計・パイプライン件数が水増しされる。`sales_pipeline` 54行もこの重複に対応。
- 対処案: 重複削除（各社1行に正規化）し、インポートを冪等化（UNIQUE制約 or upsert）。

### 問題② CSV「19社」 vs DB「18社」の不一致
- CSVは19社。DBのユニークは18社。差分はCSV 19番目 **「ビー・エスコート」**。
- `codex.md` の「18社」記述はDB側と一致、`CLAUDE.md` の「19社」はCSV側と一致。
  → ドキュメント間の食い違いの正体はこれ。

### 問題③ 破産企業が営業リストに混在
- CSV19番目「ビー・エスコート」= **2024年11月 破産・全店閉鎖**。
- 営業対象から**除外**すべき（実質的な有効ターゲットは18社）。

---

## 4. 推奨アクション

1. **チラシの実績値**: 「導入企業様の声」等の裏付けが取れるまで、数値は
   「期待効果」「目標」と明記するか、撤去する。実測が出たら `kpi_tracking` に記録して復活。
2. **DB正規化**: companies の3重登録を解消し、インポートを冪等化。
3. **営業リスト**: 「ビー・エスコート」を除外（または status=破産で営業対象外フラグ）。
4. **用語統一**: 全ドキュメントで「有効ターゲット18社（CSV登録は19社、うち1社破産）」と注記。
